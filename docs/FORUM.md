# Forum, accounts and transactional email

The 3 October 2026 owner decision replaces guest participation with verified email accounts. Reading, configuring and building remain available without an account. Reply notifications and private reports live in Your account; there is no separate activity page. Legacy `#activity` links open the account page. Threads, replies, comments, ratings, likes, public bugs and private module reports require registration. Module releases still require owner-merged GitHub PRs; a community account grants no administrator or publication privileges.

## Local draft

Use Node 24 and install dependencies. Copy `.dev.vars.example` to `.dev.vars`, set a fresh random `AUTH_SECRET` (at least 32 bytes), and keep mail settings empty. The ignored file must not be committed. Normal development uses `npm run db:local`, `npm run dev:community` and `npm run dev` as described in the app guide.

To use fictional sample discussions in an isolated local database:

```sh
node scripts/forum-preview-seed.mjs
npx wrangler dev --config wrangler.worker.jsonc --local --ip 127.0.0.1 --port 8897 --persist-to .wrangler/forum-preview
```

Set `APP_URL=http://127.0.0.1:5197` and `SESSION_TRANSPORT=bearer` in `.dev.vars`. In another terminal:

```sh
VITE_COMMUNITY_API_URL=http://127.0.0.1:8897/api npm run dev -- --port 5197 --strictPort
```

Open `http://127.0.0.1:5197/#forum`. Sign in with `demo@example.test` / `Octamod local preview 2026!`. These public demo credentials exist only in the local seed, never in migrations or runtime authentication logic. The seed has a fixed `--local` target and accepts no arguments. Never copy its database or SQL to production. Registration/recovery correctly remain unavailable without mail configuration. Automated account tests intercept mail in memory; they never send messages.

## Mail and launch setup

Keep domain registration/DNS at Hetzner. A domain-only registration does not include mailboxes. A mailbox subscription is unnecessary for sending account messages. [Resend](https://resend.com/pricing) currently offers a free sending tier of 3,000 emails/month and 100/day; confirm current limits before launch. A receiving support inbox, if wanted, is a separate service.

1. Verify `octamod.app` in Resend (the owner selected the root domain in the Ireland region). Copy the exact [SPF/DKIM DNS records](https://resend.com/docs/dashboard/domains/introduction) from that domain's dashboard into the authoritative DNS zone at Hetzner. The selected setup uses a DKIM TXT record at `resend._domainkey` and CNAME records at `rsend` and `send`. Do not replace existing website, inbound MX or root SPF records, and do not invent DNS values. The initial `_dmarc` TXT value is `v=DMARC1; p=none;`; it requests no rejection or quarantine. Review legitimate senders and delivery evidence before strengthening that policy.
2. Create a sending-only API key restricted to `octamod.app`. Store `RESEND_API_KEY`, `AUTH_SECRET` and `EMAIL_FROM` as Worker secrets with Wrangler's interactive secret input. No credentials belong in the frontend, GitHub Pages variables, commits, screenshots or PR descriptions. Set `EMAIL_FROM` to `Octamod <accounts@octamod.app>` once the domain is verified. Disable open/click tracking for verification and recovery emails so action links are not rewritten or tracked. The owner approved enforced TLS on 3 October 2026: delivery must fail if the recipient's mail server cannot accept an encrypted connection.
3. Follow [COMMUNITY_OPERATIONS.md](COMMUNITY_OPERATIONS.md) to verify an encrypted backup/isolated restore and record a D1 recovery bookmark. Apply account migrations 0011–0014 after the main issue-report migration 0010 to the chosen deployment only when deployment is authorized. Existing guest content remains intact. Deploy the API before the account frontend, keeping `REGISTRATION_OPEN=false` until public launch is approved. Login/recovery remain available to existing accounts while new signups are closed. Keep `APP_URL` equal to the frontend origin and `SESSION_TRANSPORT=bearer` for separate Pages/Worker origins. Both Wrangler configurations require `nodejs_compat`.
4. Check real inbox delivery, spam placement, DKIM/SPF/DMARC, duplicate registration, resend, expiry/replay and recovery revocation in a controlled deployment. The local draft does not prove delivery or production capacity. Test password-hashing CPU/memory against the actual Worker plan; the free CPU allowance may be insufficient for scrypt. Do not weaken password hashing to fit a hosting quota.
5. Review the public privacy copy, private account-removal request queue, operator removal/retention procedure, receiving support contact, D1 access/backups, provider logs, incident handling and dependency updates before inviting public registrations. No automatic account deletion, email-change flow, MFA or spam challenge is implemented. See [FORUM_LAUNCH.md](FORUM_LAUNCH.md) for evidence and remaining gates.

Mail is limited to verification and password recovery. No newsletters or automatic thread email. The adapter leaves plan headroom with 80 sends per UTC bucket and 2,400 per 30-day bucket. These are protective application limits, not an exact mirror of provider billing periods. Provider quotas are authoritative. Failed attempts consume quota to contain retries. Generic registration/resend/recovery acceptance also covers delivery failure/limits to avoid exposing membership; it is not a delivery receipt. The private administrator Accounts tab shows daily accepted, failed and limited counts without addresses, passwords, request bodies, provider payloads or action links. Provider acceptance does not prove inbox delivery.

Before launch approval, credentials can be staged without changing production traffic with `wrangler versions secret put <NAME> --config wrangler.worker.jsonc`. Such a version retains the existing Worker code; it is not the forum release. After deployment is authorized, upload the reviewed forum Worker with `wrangler versions upload --config wrangler.worker.jsonc`, which preserves existing secrets, and inspect the uploaded version with `wrangler versions view <VERSION_ID> --config wrangler.worker.jsonc`. Confirm all three account secrets and the existing admin secret are present, and complete the database/launch checks above before directing traffic to that version.

## Security boundaries

All source is assumed public. Security depends on server-side checks, private deployment secrets and maintained authentication code, not hidden frontend controls.

- Better Auth is pinned in the lockfile. It owns salted scrypt password hashing, signed sessions and password recovery. Only the explicitly listed facade routes are exposed: no generic auth handler, social linking or unreviewed plugin endpoint. Passwords are 15–128 characters; no passwords or session tokens appear in API JSON responses or URLs.
- Verification lasts 24 hours, requires the registration password and consumes a server-side hashed token once. Requiring the password prevents a victim from verifying an account pre-created by someone else with a password the victim does not know. Recovery lasts 30 minutes, uses a hashed token identifier, consumes it, verifies inbox ownership and revokes existing sessions and outstanding action links. Requesting links does not sign anyone in.
- Email links use the URL fragment, which is not sent with HTTP requests. The user explicitly submits the form; merely opening a message or link does not verify/reset an account. Action tokens remain sensitive, including in browser history and screenshots until completed.
- Verified, unsuspended membership is checked on the server for every participation write. Author ownership gates edits. Administrator authorization is independent and required for every moderation route; hiding, locking, pinning and suspending are recorded in private history. Suspension revokes active account and legacy sessions.
- Seven-day sessions can be ended individually by signing out, or other devices can be revoked from the account page. Password recovery revokes all sessions. Separate-origin deployments use a signed bearer in localStorage because third-party cookies are unreliable. This exposes it to same-origin JavaScript: XSS and a compromised frontend dependency are session-theft risks. Same-origin fallback uses HttpOnly, SameSite cookies, Secure on HTTPS. Production builds include a CSP meta tag for GitHub Pages, restricting scripts and connections to the app and configured API; Cloudflare also applies its response headers. Inline styles remain allowed for existing layout controls. GitHub Pages cannot enforce frame-ancestors through a meta tag. Do not add third-party scripts or unsafe HTML rendering. Rotating `AUTH_SECRET` invalidates signed credentials/verification links; also revoke stored sessions and action tokens when responding to an incident.
- CORS permits the configured app origin only; mutation requests require that Origin. JSON is limited to 32 KiB (structured device-log reports allow an additional 64 KiB), posts to 12,000 characters and results are paginated. SQL values are bound. Dynamic moderation columns/tables come only from fixed allowlists. Posts render as escaped React text with paragraphs, grouped `>` quotes and fenced code blocks. Formatting does not interpret HTML, markdown links or executable URLs; code remains text and is never executed.
- Persistent D1 limits cover IPs (the trusted Cloudflare connecting-IP header), email addresses and member actions. Keys are time-bucketed hashes. They are pseudonymous abuse controls, not a claim of strong anonymization. Reverse proxies on future self-hosting must strip spoofed forwarding headers. A distributed attacker or a compromised inbox remains a risk; add edge abuse controls if actual traffic requires them.
- Shared configurations accept only name, module IDs, exact version strings and the stock-FX2 choice. They are immutable post snapshots, with explicit local copy/import. Import selects the current approved catalog versions and reruns normal compatibility checks. It never executes a post or downloads firmware. Arbitrary JSON fields, uploads and firmware attachments are rejected. Public prose cannot automatically prove copyright compliance; moderation and contributor responsibility still apply.

## Stored information and operations

`auth_users` holds private email, username and verification state. `auth_accounts` holds credential hashes; `auth_sessions` holds library session records without IP/user-agent values. Public community queries use a separate `users` projection and never return email/password/token columns. Signed bearer verification means the raw database session token alone is insufficient to authenticate.

Posts/usernames/config snapshots are public. Private reports, bookmarks, follows, notifications and moderation history are permission-scoped. New account reports include structured configuration and a validated device log, or an explicit missing-log reason. They do not open GitHub issues; the privacy migration grants no publication permission and retries reject private records. Previously published reports retain their existing GitHub links. A new public-sharing workflow needs separate review and approval. Historical guest names are unverified and cannot reserve or claim accounts. Signing in replaces that browser's guest session; there is no automatic migration of private reports by name or email.

Hourly cleanup removes expired action tokens, sessions and throttle rows. Forum content, pending registrations, reports, aggregate mail counters and moderation history persist until operator removal; notifications are limited in the response but are not purged on a retention schedule. Your account accepts private removal requests with the current password and an explicit confirmation; requests remain reversible while pending. Separate administrator review is private and cannot claim completion while credentials/private data remain. Actual removal needs an authorized operator procedure and an agreed public-content handling decision, as documented in [COMMUNITY_OPERATIONS.md](COMMUNITY_OPERATIONS.md); submitting a request never immediately erases data.

Run `npm run check` for ordinary app checks, including authentication/authorization regression tests and a production frontend build. Tests cover verification/recovery, replay/expiry, forged sessions, origin checks, legacy ownership, immutable config validation and moderation. They use synthetic data only. No firmware, emulator, hardware or DSP qualification tests are needed for forum work. Keep the authentication dependency patched and review security advisories; passing these tests is not an independent security audit.
